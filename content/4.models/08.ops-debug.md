## 评测目标

运维排查的核心不是给出通用命令，而是先确认真实状态，再提出最小变更。模型必须能区分历史文档、用户记忆和当前主机读回。

## 任务集

| 任务 | 必须证据 | 失败信号 |
| --- | --- | --- |
| 端口不通 | `ss`/`netstat`、防火墙、客户端探测 | 只说“打开端口” |
| systemd 服务异常 | `systemctl status`、`journalctl` | 不读日志直接改配置 |
| 代理问题 | 环境变量、curl、provider 返回 | 混淆浏览器和终端网络 |
| SSH 问题 | 本地配置、远端服务、转发链路 | 只重装客户端 |

## 推荐模型配置

Deep 路由通常足够。跨多台机器、涉及迁移或需要长时间追踪日志时再使用 Max 路由。

## 验收方式

最后必须给出：

1. 当前 live state。
2. 实际修改了什么。
3. 是否重启服务。
4. 从服务端和客户端分别如何验证。

## 证据命令

| 层级 | Linux 常用命令 | Windows 客户端常用命令 |
| --- | --- | --- |
| 进程 | `ps aux`、`systemctl status <service>` | `Get-Process` |
| 监听 | `ss -lntp`、`netstat -lntp` | `Get-NetTCPConnection` |
| 日志 | `journalctl -u <service> -n 100` | 事件查看器或应用日志 |
| 连通性 | `curl -v`、`nc -vz` | `Test-NetConnection`、`curl.exe -v` |
| 配置读回 | `cat`、`grep`、服务专用 inspect 命令 | `Get-Content` |

## 评分扣分项

| 问题 | 扣分原因 |
| --- | --- |
| 只引用旧文档 | 没有确认 live state |
| 未区分本地和远端 | 容易把客户端代理问题误判成服务端问题 |
| 修改前不备份或不读回 | 无法证明改动最小且正确 |
| 用户说手动重启后仍强行重启 | 越过操作边界 |

运维排查的结论应该先给事实，再给解释。事实包括主机、端口、服务名、配置路径、日志片段和客户端探测结果。
