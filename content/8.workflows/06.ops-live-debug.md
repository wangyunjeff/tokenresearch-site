## 场景

服务无法访问、端口不通、代理异常或远程任务失败时，最容易出错的是相信旧文档，而不是读取当前机器状态。

## 推荐路线

1. 先用 [Ops Debug](/gallery/ops-debug) 的方式读取当前服务、端口、日志和配置。
2. 如果涉及模型或 API，再看 [成本与速度评测](/models/cost-speed) 和 [工具调用评测](/models/tool-use)。
3. 每次只做一个最小修改，并在修改后读回配置。
4. 如果用户明确说手动重启服务，就停在配置读回，不擅自重启。

## 状态读取模板

```text
本地:
- 访问的域名/IP:
- 端口:
- 客户端错误:

远端:
- 服务名:
- 配置文件:
- 监听端口:
- 最近日志:
```

## 最小命令组

| 层级 | 示例 |
| --- | --- |
| 本地 | `Test-NetConnection host -Port 443` 或 `curl -v` |
| 远端服务 | `systemctl status service` |
| 远端监听 | `ss -lntp` |
| 日志 | `journalctl -u service --since today` |
| 配置 | 读回目标配置文件，不只依赖记忆 |

## 模型路由

日常命令解释可用 Fast 路由。真实服务器排查建议 Deep 路由。跨服务迁移、数据库合并或长时间 cutover 才考虑 Max 路由。

## 验收

- 明确本地和远程分别执行哪些命令。
- 给出真实端口、服务名、配置文件路径和日志证据。
- 修改后读回配置，并做客户端连通性验证。
- 不把旧笔记当成当前状态。

## 失败信号

如果回答里没有 live probe、没有具体路径、没有端口或服务名，说明排查证据不足。先补状态读取，再谈修改。
