## 模型

按任务复杂度选择合适模型，避免为简单任务长期使用高成本配置。

## 任务路由

| 任务 | 建议配置 |
| --- | --- |
| 快速问答 | 快速模型或低预算 |
| 代码审查 | 更强推理，要求给出文件行号 |
| 跨文件修改 | 更强模型，并要求修改后运行检查 |
| 研究和论文 | 长上下文，保留证据和引用 |

## 对照 Codex 的记录字段

| 字段 | 为什么记录 |
| --- | --- |
| 工具表面 | CLI、插件和桌面端上下文不同 |
| 模型名 | 必须写 exact slug 或界面显示名 |
| 推理预算 | 判断成本、速度和稳定性 |
| 文件读取 | 是否读到真实入口和规则文件 |
| 验证命令 | 是否真的跑了项目脚本 |

## 评估方式

不要只看一次输出是否漂亮。更重要的是记录它是否：

- 找到真实入口文件。
- 能遵守项目约束。
- 能在失败后自我修正。
- 能说清楚未验证的部分。

这些维度可以和 [Codex 模型测试](/codex/model-test) 使用同一张记录表。

## 降级信号

如果任务只是解释一段代码、生成短文案或修改一个 Markdown 段落，就不需要长期使用最高预算。把省下的预算留给长上下文审查、复杂重构和研究写作。
